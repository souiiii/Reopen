Reopen UI/UX Fix — 18-Phase Implementation Plan
New Product Direction

Before the phases, the core product interaction should change to this:

Reopen should no longer behave like “a menu that opens windows.”
It should behave like a compact workspace hub anchored to the menu bar.

That means:

no separate Create Workspace window
no separate Manage Workspaces window
no separate Launch Result window
no raw text-only workspace list
no workflow that forces the user into multiple UI contexts

Instead:

clicking the menu bar icon opens a single custom panel
that panel contains:
workspace list
inline create flow
inline edit flow
inline delete controls
visual workspace summaries
subtle launch feedback


The repo already has separate areas for menu bar UI, workspace editor windows, launch result windows, runner logic, workspace models, storage, settings, and permissions, so this plan intentionally changes the UX layer without rewriting the stable launch/storage system underneath. 

# Expanded UI/UX Fix Plan — 18 Phases

## Phase 1 — Audit Current UI Flow and Freeze the New UX Direction

### Goal

Document exactly what must be removed, kept, and replaced.

### Tasks

* Identify all current entry points:

  * menu bar dropdown
  * create workspace window
  * manage workspaces window
  * launch progress window
  * launch result window
  * settings window
* Mark which flows are being replaced.
* Confirm the new primary UX:

```text
Menu bar icon → unified workspace panel → create/edit/delete/launch inline
```

### Deliverable

A short internal document: `docs/ui-redesign-scope.md`.

### Acceptance Criteria

* The agent knows which old windows are being replaced.
* The launch engine, storage, workspace models, and permissions are confirmed as reusable.
* The redesign is scoped as UX replacement, not a full app rewrite.

---

## Phase 2 — Add a Temporary Feature Flag for the New UI

### Goal

Allow the new panel to be built without destroying the old working UI immediately.

### Tasks

* Add a setting or compile-time flag:

```swift
useUnifiedWorkspacePanel = true
```

* Keep the old menu/window flow available during development.
* Route menu bar clicks to either:

  * old `NSMenu` flow
  * new unified panel flow

### Deliverable

A safe toggle between old and new UI.

### Acceptance Criteria

* App still builds.
* Old UI still works while new UI is incomplete.
* New UI can be developed incrementally.

---

## Phase 3 — Replace the Plain Menu with a Custom Anchored Panel Shell

### Goal

Create the new surface that opens from the menu bar icon.

### Tasks

* Build a new custom panel component:

  * `WorkspaceHubPanelController`
  * `WorkspaceHubPanelView`
* Use either:

  * `NSPopover`, or
  * borderless transient `NSPanel`
* Anchor it to the menu bar status item.
* Make it dismiss when clicking outside.
* Make it stay open during creation/editing.
* Give it an initial fixed size, for example:

```text
Width: 420–520 px
Height: 560–680 px
```

### Deliverable

A blank but functional menu-bar-attached panel.

### Acceptance Criteria

* Clicking the Reopen menu bar icon opens the custom panel.
* The panel is not a standard text dropdown.
* It can display SwiftUI content.
* It closes naturally when dismissed.
* It does not open the old create/manage windows.

---

## Phase 4 — Create Panel Navigation and UI State

### Goal

Give the panel its own internal state system.

### Tasks

Create a state model such as:

```swift
enum WorkspaceHubMode {
    case list
    case creating
    case editing(workspaceID: UUID)
    case launchDetails(workspaceID: UUID)
}
```

Track:

* selected workspace
* expanded card
* create composer open/closed
* edit mode
* delete confirmation state
* launch status per workspace
* validation messages

### Deliverable

A clean state layer for the new panel.

### Acceptance Criteria

* The panel can switch between list, create, and edit states.
* State changes do not require opening new windows.
* State resets correctly when the panel closes.
* The code does not mix launch logic directly into view code.

## Phase 6 — Build Workspace Summary Logic

### Goal

Generate a readable visual summary of each workspace.

### Tasks

Create a helper such as:

```swift
WorkspaceSummaryBuilder
```

It should calculate:

* number of apps
* number of files
* number of folders
* number of URLs
* number of terminal commands
* number of VS Code projects
* whether window restore is enabled
* app icons or fallback symbols
* short generated description

Example generated summary:

```text
3 apps · 2 links · 1 folder · Terminal
```

### Deliverable

A reusable workspace summary model.

### Acceptance Criteria

* Every workspace can produce a display summary.
* Empty workspaces show a useful state.
* Cards do not need to inspect raw action arrays directly.
* The summary handles all existing action types.

## Phase 7 — Build the Workspace Card Component

### Goal

Replace plain text workspace rows with visual workspace cards.

### Tasks

Create:

```text
WorkspaceCardView
```

Each card should show:

* workspace name
* generated or saved description
* visual action preview
* app/icon row
* chips/counts
* launch affordance
* edit button
* delete button
* optional duplicate/menu button

### Interaction Rules

* Clicking the main card area launches the workspace.
* Clicking edit enters inline edit mode.
* Clicking delete starts inline confirmation.
* Buttons should not feel visually noisy.

### Deliverable

Reusable card view.

### Acceptance Criteria

* A workspace is no longer represented as plain text.
* User can understand what the workspace contains at a glance.
* Edit/delete controls are available directly on the card.
* The card feels polished and native.

## Phase 9 — Change Workspace Naming Rules

### Goal

Make workspace name optional and auto-generate names.

### Tasks

Currently, the app treats empty names as invalid. Change that behavior at the right layer.

Add logic such as:

```swift
WorkspaceNameGenerator.nextName(existingWorkspaces)
```

Rules:

```text
Blank name → Workspace 1
Next blank name → Workspace 2
If Workspace 2 exists → Workspace 3
```

Update:

* workspace creation draft
* workspace validator
* workspace manager create path
* UI validation message
* tests

### Deliverable

Optional workspace names with automatic fallback.

### Acceptance Criteria

* User can save a workspace without typing a name.
* Blank names become `Workspace N`.
* Existing custom names are not overwritten.
* Duplicate auto-generated names are avoided.
* Tests cover auto-name behavior.

## Phase 16 — Replace Progress and Result Windows with Quiet Inline Feedback

### Goal

Remove the disruptive launch result screen.

### Tasks

Change launch feedback behavior:

### During launch

Show on the workspace card:

```text
Launching…
```

with a small spinner/progress indicator.

### On success

Show subtle temporary state:

```text
Launched
```

Then fade back to normal.

### On failure

Show inline warning:

```text
Some items failed
Show details
```

When expanded, show:

* failed item
* reason
* repair action if available

### Important

Do not delete existing launch result data models.
Only stop presenting the separate result/progress windows by default.

### Deliverable

Quiet launch feedback inside the panel.

### Acceptance Criteria

* Successful launch does not open a new result window.
* Launch progress does not open a new progress window.
* Failures are still visible and recoverable.
* The user’s flow is not interrupted.

Use this order exactly:

```text
1. Audit current UI flow
2. Add feature flag
3. Build custom anchored panel
4. Add panel state/navigation
5. Add design system
6. Add workspace summary builder
7. Build workspace cards
8. Build workspace list
9. Add auto workspace naming
10. Build inline create composer
11. Add inline action adders
12. Add compact action editing
13. Wire inline create save/cancel
14. Build inline workspace editing
15. Add inline delete/duplicate/reorder
16. Replace launch result windows with inline feedback
17. Move secondary utilities into calm footer/settings
18. Remove old primary routes and run full QA
```

# The Key Rule for the Agent

Do **not** rewrite the backend systems unless necessary.

The existing app already has working workspace models, storage, launch execution, permissions, settings, and import/export. The redesign should mostly replace the **presentation and workflow layer**, while continuing to use the stable underlying managers and runner services.
